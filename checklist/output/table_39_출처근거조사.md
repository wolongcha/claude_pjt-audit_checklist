## 1. Agentic AI 적용 범위 및 역할 정의

#### [3-1-다-1-01]: Agentic AI 적용 대상 업무가 명확히 정의되었는가?
* **검토 내용**:
    * AI 챗봇, AI 지식검색, 문서생성, 업무자동화Bot 대상 업무 식별
    * 단순 응답형 AI와 Agentic AI 기반 자동화 업무 구분
* **출처 문헌**:
    * [AI보안가이드북] 제3장 제1절 가.개념도(그림32) — "에이전틱 AI(Agentic AI): 특정 목표를 해결하기 위해 다수 AI 에이전트가 상호 작용하며 계획수립, 외부 정보 기억, 도구 호출 등을 사용자의 개입 없이 자율성을 가지고 수행", "(요청)사용자가 에이전틱 AI에 임무 요청 → (계획)에이전트별 목표달성을 위한 행동방침 수립 → (행동)외부 도구 등을 활용, 작업 수행"
    * [AI위협매뉴얼] 제1장 제2절(원문 p.15) — "LLM 애플리케이션: LLM을 핵심 두뇌로 두고 도구·에이전트·외부 데이터와 결합해 사용자 요청을 처리하는 단일 서비스"; "에이전트는 LLM이 목표 달성을 위해 자율적으로 도구를 호출하며 단계별 작업을 수행하는 실행 단위"; 별첨3 용어집 #31(에이전트), #56(LLM 애플리케이션), #11(다중 에이전트 — "복수 에이전트가 협력·상호 작용하여 복잡한 작업을 처리하는 구성")
    * [수행가이드] Ⅱ장 요구정의단계 감리, TTAK.KO-11.0103 소프트웨어 요구사항품질평가항목 — 완전성(Completeness): "요구사항명세서상에 식별된 요구사항 중 사용자가 제시한 요구사항에서 누락된 기능 요구사항이 존재하는지 여부"(필수 우선적용항목)
* **근거 및 상세내용**:
    * [AI보안가이드북]과 [AI위협매뉴얼]이 공통으로 제시하는 "에이전틱 AI/에이전트"의 정의(자율적 계획수립과 도구호출을 통한 다단계 작업 수행)와 "LLM 애플리케이션"(단일 응답 생성 서비스)의 정의는, "단순 응답형 AI와 Agentic AI 기반 자동화 업무"를 구분해야 한다는 세부 검토내용의 핵심 판별기준을 직접 제공한다. 즉 사용자 질의에 텍스트 응답만 생성하는 업무는 LLM 애플리케이션 영역이고, 계획수립 → 도구호출 → 행동을 사용자 개입 없이 자율 수행하는 업무가 Agentic AI 적용 대상이라는 구분 기준이 성립한다.
    * [수행가이드]의 요구사항 품질기준(완전성)은 "적용 대상 업무" 식별이 요구사항정의서상에 누락 없이 열거되어야 함을 요구정의단계 감리의 공통원칙(TTA 국가표준 근거)으로 규정하여, "명확히 정의되었는가"라는 본 항목의 감리방법론적 근거가 된다.
    * 다만 "AI 챗봇, AI 지식검색, 문서생성, 업무자동화Bot"이라는 4개 세부 업무 분류체계 자체가 1순위 문헌에 그대로 열거되어 있지는 않다(동일 도메인의 요구정의단계 다른 카테고리(가.사업관리, 나.AI모델 및 RAG)에서 사용되는 서비스유형 분류와 정합하는 체크리스트 고유의 업무 예시로 판단됨) — 이 열거 자체의 출처는 확인 필요.

## 3. A2A 연계 요구사항 정의

    * [AI보안가이드북]이 명시하는 구글 A2A(Agent-to-Agent) 프로토콜 및 "계획·상태정보·메시지 교환" 통신요소는 본 항목의 "Agent 간 메시지 전달 범위 및 데이터 공유 기준 정의"에 대한 직접적 프로토콜 수준의 근거이다.
    * A-M15(신원확인)·A-M16(통신구간보호)·A-M08(최소권한 통신)은 "Agent 간 호출 가능 조건 및 제한 기준"의 구체적 보안 통제 항목으로 직접 대응하며, A10 위협 정의는 이러한 통제가 없을 경우의 위험을 역으로 뒷받침한다.
    * [AI위협매뉴얼]의 "멀티 에이전트 간 무한 위임 테스트"는 에이전트 간 책임소재가 불명확할 때 발생하는 구체적 실패 시나리오(책임 떠넘기기, 무한 루프)를 제시하여, Agent 간 통신·호출관계에 "범위와 조건"이 사전에 명확히 정의되고 상한이 설정되어야 한다는 감리상 필요성을 실증적으로 뒷받침한다.
    * "요청 Agent, 검색 Agent, 응답 Agent, 검증 Agent"라는 4개 역할의 구체적 명칭 구분 자체는 1순위 문헌에 그대로 제시되어 있지 않아 확인 필요(체크리스트가 예시로 제시하는 전형적 멀티에이전트 파이프라인 패턴으로 판단됨 — [AI위협매뉴얼]의 "기획자 에이전트/실행 에이전트" 구분이 유사한 역할분리 사례로 참고 가능).

## 4. Agent–RAG 연계 요구사항

#### [3-1-다-4-01] (A): Agent와 RAG 검색 연계 요구사항이 정의되었는가?
* **검토 내용**:
    * Agent가 호출할 지식검색 대상과 범위 정의
    * 기록물관리, 민원통합, 사규, FAQ 등 RAG 데이터별 호출 기준
    * 검색 결과를 Agent가 응답에 활용하는 기준
* **출처 문헌**:
    * [AI보안가이드북] 제3장 제1절 가.개념도(요소별 설명, p.65) — "메모리: ... 장기 메모리: 외부 지식, 과거 사용자 상호작용 등 개인화 정보를 축적하고 있는 RAG 벡터DB 등 저장소"
    * [AI위협매뉴얼] 제1장 제3절 체크리스트 M02(벡터DB·임베딩 유출) — "벡터DB 및 임베딩 저장소에 대한 접근 권한을 통제하는가", "벡터DB 또는 RAG 검색 결과에 포함된 민감정보가 모델 출력에 노출되지 않도록 관리하는가"
    * [AI위협매뉴얼] 별첨3 용어집 #3(검색 증강 생성, RAG — "외부 저장소를 검색해 LLM 답변 생성을 보조하는 기법"), #37(인덱스 테넌트 — "RAG 시스템에서 검색 및 조회 대상이 되는 색인(Index)을 조직이나 사용자 그룹별로 분리해 두는 논리적 공간")
    * [AI위협매뉴얼] 제4장 제1절 1.1(다중에이전트 관련 확장, 원문 p.~) — "다중 에이전트 환경에서는 각 에이전트의 역할과 권한을 최소화하여 불필요한 내부·외부 자원 접근을 차단해야 한다"
    * [AI위협매뉴얼] 제3장 제3절 공공·행정 시나리오2 "업무 보조 AI를 통한 내부 기밀문서 유출"(원문 p.78~80) — 보안 취약 지점으로 "인덱스 테넌트 및 보안 등급 분리 미비", "문서 접근 제어 목록, 민감도 라벨 누락 또는 검색 시 미적용" 제시
* **근거 및 상세내용**:
    * [AI보안가이드북]이 RAG 벡터DB를 Agent의 "장기 메모리"로 명시적으로 위치시키는 것은, "Agent가 호출할 지식검색 대상과 범위"를 정의해야 한다는 본 항목의 구조적 근거를 제공한다 — RAG는 Agent 아키텍처상 임의의 외부 서비스가 아니라 Agent 자체의 지식기반 구성요소로 다루어져야 함을 시사한다.
    * [AI위협매뉴얼] M02와 "인덱스 테넌트" 개념은 "RAG 데이터별 호출 기준"이 조직·업무 단위(예: 기록물관리/민원통합/사규/FAQ 등 데이터군별)로 분리·통제되어야 함을 뒷받침하며, 공공·행정 시나리오2가 지적하는 "인덱스 테넌트 및 보안등급 분리 미비"라는 실패사례는 RAG 데이터별 호출기준이 없을 때 발생하는 구체적 위험(내부 기밀문서 유출)을 실증한다. "다중 에이전트 환경에서 각 에이전트의 역할과 권한을 최소화" 원칙은 Agent별로 호출 가능한 RAG 데이터 범위가 차등화되어야 한다는 근거를 제공한다.
    * 다만 "기록물관리, 민원통합, 사규, FAQ"라는 구체적 업무영역별 RAG 데이터 분류 자체와 그에 따른 개별 호출기준은 1순위 문헌에서 확인되지 않아 확인 필요(해당 세부내용은 동일 도메인 "나.AI 모델 및 RAG" 카테고리의 RAG 적용범위 요구사항과 상당 부분 중복되는 영역으로, Agent 관점에서는 위 근거들이 구조적 뒷받침을 제공하는 수준이다).

#### [3-1-다-4-02] (B): 다중 검색 및 질의 확장 기준이 정의되었는가?
* **검토 내용**:
    * Agent의 질의 재작성 및 질의 확장 기준
    * 키워드 검색, 벡터 검색, 하이브리드 검색 선택 기준
    * 다중 검색 결과 통합 및 우선순위 기준
* **출처 문헌**:
    * [AI위협매뉴얼] 별첨3 용어집 #3(RAG), #22(벡터DB — "임베딩 벡터를 저장·검색하는 데이터베이스. RAG에 활용"), #37(인덱스 테넌트)
    * 확인 필요 — 질의 재작성(query rewriting)·질의 확장(query expansion), 키워드/벡터/하이브리드 검색 선택기준, 다중검색결과 통합·재순위화(re-ranking) 등 정보검색(IR) 기법 자체의 선택·설계기준은 1순위 문헌(AI보안가이드북, AI위협대응매뉴얼, 감리수행·발주관리가이드, AI 데이터 품질관리 가이드 제1~3권 등 priorsource\생성형AI 폴더 전체) 어디에서도 확인되지 않음
* **근거 및 상세내용**:
    * [AI위협매뉴얼]은 벡터DB·RAG의 존재와 그 보안관리 필요성(접근통제, 인덱스 분리)만 다룰 뿐, 질의 재작성·질의 확장·하이브리드 검색(키워드+벡터 결합)·재순위화 등 정보검색 기법 자체의 선택기준이나 다중검색결과 통합기준은 1순위 문헌 어디에서도 다루어지지 않는다. AI 데이터 품질관리 가이드(제1권~제3권)도 라벨링·측정지표(Top-K 정확도 등 모델평가지표) 위주로, 검색엔진의 질의처리·랭킹 기법을 감리기준 형태로 규정하고 있지 않음을 확인하였다.
    * 이는 보안/감리방법론 문헌이 아니라 정보검색(IR) 기술론 영역에서 다루어질 사안으로 판단되며, 스킬 2순위 범위(ISO/TTA/논문) 중에서도 "질의확장·하이브리드검색 선택기준"을 감리 관점의 규범적 기준으로 명시한, 실제 원문을 확인한 문헌을 찾지 못하여 확인 필요로 처리한다.
    * 참고로 본 항목은 원본 파일상 일련번호가 [3-1-다-4-01](A)와 동일하게 "01"로 중복 부여되어 있으나, 카테고리 내 두 번째 항목이라는 위치와 내용상 (A)의 RAG 연계 "범위·기준" 정의에 이어지는 세부 기법 항목이라는 점에서 실질적으로는 "4-02"에 해당하는 것으로 판단된다(본 조사에서는 원본 표기와 사용자 안내에 따라 (A)/(B)로만 구분하고 원본 번호 자체는 임의로 수정하지 않았다).

    * "내부업무시스템API, 검색API, 법령검색API, 문서생성Tool"이라는 구체적 Tool 유형 열거 자체는 1순위 문헌에 없어 확인 필요(체크리스트 고유의 공공업무 예시로 판단).

## 6. Agent 보안 및 권한 요구사항

#### [3-1-다-6-01]: Agent 실행 권한 기준이 정의되었는가?
* **검토 내용**:
    * 사용자·부서·직무별 Agent 사용 권한 기준
    * Agent별 접근 가능한 데이터 및 Tool 범위 정의
    * 관리자·운영자·일반사용자 권한 구분
* **출처 문헌**:
    * [AI위협매뉴얼] 제4장 제2절 1.1 최소 권한·역할 기반 접근 제어(원문 p.143~144) — "AI 에이전트는 일반적으로 사용자의 권한을 대리하여 작업을 수행하며... 최소 권한 원칙과 역할 기반 접근 제어를 권장"; "AI 에이전트의 권한은 역할별로 세분화하여 관리해야 하며... 필요한 경우에는 임시 권한을 부여하고, 작업 종료 후 자동 회수되도록 설계"
    * [AI위협매뉴얼] 1.4 실행 권한 정보 분리 관리(원문 p.146~147) — "정책 엔진은 역할 기반(RBAC) 또는 속성 기반(ABAC) 규칙에 따라 접근을 허용·거부하며, 모든 호출 결과를 감사 로그에 기록하면 사용자의 권한, 요청 목적, 접근 리소스 간의 일관된 통제와 추적 가능성을 확보"
    * [AI보안가이드북] 나.보안위협 A04(AI의 무단 권한 침해), 다.보안대책 A-M06(미승인 에이전트 권한 위임 차단), A-M11(과도한 권한 부여 제한)
    * [AI위협매뉴얼] 별첨3 용어집 #26 — "사용자·운영자 경계(Identity Boundary): LLM 시스템 내 사용자·운영자·에이전트·외부 도구 간 역할·권한이 구분되는 경계"
* **근거 및 상세내용**:
    * [AI위협매뉴얼] 1.1의 역할기반접근제어(RBAC) 권고와 "사용자의 권한을 대리한다"는 설명은 "사용자·부서·직무별 Agent 사용 권한 기준"이라는 세부 검토내용의 직접적 설계원칙을 제공한다.
    * 1.4의 정책엔진(RBAC/ABAC)이 "사용자의 권한, 요청목적, 접근리소스 간의 일관된 통제"를 감사로그로 확보한다는 설명은 "Agent별 접근 가능한 데이터 및 Tool 범위 정의"의 구체적 구현모델을 제공하며, 별첨3 "사용자·운영자 경계(Identity Boundary)" 정의는 "관리자·운영자·일반사용자 권한 구분"이라는 세부 검토내용과 개념적으로 정확히 대응한다.
    * [AI보안가이드북]의 A04/A-M06/A-M11은 이러한 권한체계가 미비할 경우의 위협(무단권한침해)과 그 대응책(미승인 위임 차단, 과도한 권한부여 제한)을 보안 관점에서 보강한다.

## 9. 책임성 및 Human-in-the-Loop 요구사항

#### [3-1-다-9-01]: Agent 처리 결과에 대한 검토·승인 체계가 정의되었는가?
* **검토 내용**:
    * 민원 답변, 문서생성, 외부 전송 등 사용자 승인 필요 업무 정의
    * Agent 결과의 담당자 검토 및 수정 절차 정의
    * 자동처리와 사람 검토 업무의 구분 기준
* **출처 문헌**:
    * [AI위협매뉴얼] 제4장 제2절 1.2 Human-in-the-Loop(원문 p.144, 전문) — "AI 시스템을 통한 자동화가 더욱 폭넓게 적용될수록 의사결정 과정에서 인간의 개입을 적절하게 보장하는 것은 안전성 확보를 위한 핵심 요소이다. Human-in-the-Loop(HITL) 접근 방식은 AI가 독자적으로 중요한 결정을 내리지 않도록 하고 반드시 인간 검증 과정을 거치도록 함으로써 악의적인 입력으로 인한 잘못된 결정을 차단하는 효과적인 방법 중 하나이다. 예를 들어 금융 거래, 의료 진단, 보안 정책 변경 등 고위험 영역에서는 AI가 제안한 조치가 자동 실행되지 않고, 반드시 승인 절차를 거치도록 하는 것이 바람직"; 가.위험 기반 접근법 — "단순 정보 제공이나 일반적인 권고 사항은 자동으로 처리하되, 민감한 정보 접근이나 시스템 설정 변경과 같은 고위험 조치에 대해서만 인간 승인을 요구"
    * [AI위협매뉴얼] 별첨3 용어집 #25 — "사람 개입(HITL, Human-in-the-Loop): 고영향 작업 실행 전 사람의 승인 절차"
    * [AI위협매뉴얼] 1.3 에이전트 가드레일 도입 나.행동 범위 제한(원문 p.145~146) — "파일 삭제, 외부 송금, 대량 데이터 전송과 같은 고위험 행동은 기본적으로 차단하거나, 별도의 승인 절차(HITL)와 연계하여 통제"
    * [AI보안가이드북] 나.보안위협 A09(과도한 인간 개입 유발로 과부하 발생), 다.보안대책 A-M12(민감 명령 승인 절차 마련), A-M13(민감 명령 승인 요청 임계값 설정 — "민감 명령 우선순위에 따라 임계값을 설정하여 과도한 승인 요청이 발생하지 않도록 구성")
    * [AI위협매뉴얼] 제3장 제3절 공공·행정 시나리오4 "AI 인허가 검토 시스템을 통한 부적격 승인 유도"(원문 p.82~84) — "AI 에이전트는 승인 가능 판정을 제안. 담당자는 AI 권고를 그대로 반영하여 최종 승인 발급 처리"; 보안 취약지점 "AI 판단을 인간 검토자가 맹신하거나 검증 없이 승인 절차에 반영"
