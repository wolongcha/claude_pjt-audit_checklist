#### [3-2-다-1-01]: Agentic AI 구조가 요구사항에 맞게 설계되었는가?
* **검토 내용**:
    * Agent, LLM, RAG, Tool/API, 업무시스템 간 연계 구조 설계
    * 단일 Agent / 다중 Agent 적용 범위 구분
    * 챗봇, 지식검색, 문서생성, 업무자동화별 Agent 구조 반영
* **출처 문헌**:
    * [AI보안가이드북] 제3장제1절가.개념도 "에이전틱 AI(Agentic AI)" — "특정 목표를 해결하기 위해 다수 AI 에이전트가 상호 작용하며 계획수립, 외부 정보 기억, 도구 호출 등을 사용자의 개입없이 자율성을 가지고 수행", "(요청)사용자가 에이전틱AI에 임무요청→(계획)에이전트별 목표달성을 위한 행동방침수립→(행동)외부 도구 등을 활용, 작업수행". 요소별설명: "계획", "메모리(단기/장기 — RAG 벡터DB 등 저장소)", "도구호출(MCP 등 표준 프로토콜을 활용하여 MCP 서버를 통해 연결된 외부 도구를 호출)", "에이전트 통신(구글의 A2A 프로토콜 등)"
    * [AI보안가이드북] 사례("에이전틱 AI를 활용한 행정 원스톱 서비스") — "각 내・외부 도구와 MCP서버를 통해 연동되어 있는 다수 AI에이전트를 연계, 동일 목표달성을 위해 동작하도록 구성", "활용방법: 출장, 휴가, 예산신청 등 행정업무자동화"

* **근거 및 상세내용**:
    * 개념도의 "계획→도구호출→에이전트통신" 요소별 설명 자체가 Agent가 LLM(계획수립의 추론엔진 역할)・RAG(장기메모리로서의 벡터DB)・Tool/API(도구호출)・타 Agent(에이전트통신)와 연계되는 구조를 규정하므로 "Agent, LLM, RAG, Tool/API, 업무시스템 간 연계 구조 설계"의 직접 근거이다.
    * 활용사례의 "다수 AI에이전트를 연계, 동일 목표달성을 위해 동작하도록 구성"이 "단일/다중 Agent 적용범위 구분"의 실사례 근거이며, "출장・휴가・예산신청 등 행정업무자동화"가 검토내용의 "업무자동화" 유형에 정확히 대응한다.
    * [감리점검해설서] SD12-1은 생성형AI 특화 문헌은 아니나, "설계단계 시스템 구성요소 분할・배치・인터페이스 설계"를 점검하는 일반 감리방법론으로서 Agent 아키텍처 설계 검토 절차의 방법론적 근거를 제공한다.
    * 다만 "챗봇, 지식검색, 문서생성, 업무자동화"라는 4개 세부 업무유형별로 Agent 구조를 구분・반영하도록 명시한 조항은 1순위 문헌에서 확인되지 않았으며, 2순위 웹검색에서도 이 4유형 분류체계를 명시한 공식 문헌을 찾지 못하여 확인 필요로 남긴다.

## 2. MCP 연계 설계

#### [3-2-다-2-01]: MCP 기반 Tool 연계 구조가 적정하게 설계되었는가?
* **검토 내용**:
    * MCP Server, MCP Client, Tool Registry 구성 정의
    * Agent별 호출 가능한 Tool 목록 및 권한 범위 정의
    * Tool 입력값·출력값·호출조건·응답형식 표준화
* **출처 문헌**:
    * [AI보안가이드북] "MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)" — "엔트로픽에서 제안한 AI 에이전트와 외부 도구, 데이터, API 간의 상호작용을 표준화하여 연결해주는 프로토콜로 대규모 AI환경에서 유연성과 재사용성 제고", "(요청)AI 에이전트가 요청 해석, 계획을 수립하여 MCP 서버 전달 → (작업)MCP 서버는 외부 시스템과 상호작용, 실제 작업 수행"
    * **(2026-08-13 추가조사・3순위 업계 사실상 표준)** Anthropic 공식 MCP 스펙(modelcontextprotocol.io, GitHub `modelcontextprotocol/modelcontextprotocol`) — MCP는 JSON-RPC 2.0을 전송계층으로 사용하며, 메시지 스키마를 TypeScript로 우선 정의한 뒤 JSON Schema로 공개하여 MCP Server・Client・Tool 간 요청/응답 형식을 표준화한다. "Tool 입력값・출력값・호출조건・응답형식 표준화"라는 본 항목의 세부 검토내용이 바로 이 공식 스펙이 규정하는 메시지 스키마 표준화 대상이다.
    * [AI위협매뉴얼] A01(부적절한 도구 설계) 평가기준[양호] — "사용자 또는 권한별로 LLM이 사용할 수 있는 도구를 제한하고 있는 경우", "MCP 서버별로 접근 가능한 리소스가 명확히 제한되어 있는 경우" / 진단방법 — "MCP 환경에서는 mcp.json과 같은 MCP 서버 설정 파일을 검토하여 각 서버의 allowed_paths, blocked_commands 등 접근 제한 설정이 적절한지... 단일 MCP 서버가 과도하게 많은 리소스에 접근할 수 있도록 설정되어 있지 않은지... 확인한다"
* **근거 및 상세내용**:
    * MCP의 공식정의("AI 에이전트와 외부 도구, 데이터, API 간 상호작용을 표준화하여 연결")와 요청-작업 흐름(AI에이전트↔MCP서버↔외부시스템)이 "MCP Server, MCP Client, Tool Registry 구성 정의"의 개념적 근거이다.
    * A01 평가기준의 "권한별 도구 제한", "MCP서버별 접근가능 리소스 제한"이 "Agent별 호출 가능한 Tool목록 및 권한범위 정의"의 직접 근거이며, mcp.json의 allowed_paths・blocked_commands 검토방법이 이를 기술적으로 구체화한다.
    * "Tool 입력값・출력값・호출조건・응답형식 표준화"는 평가기준의 "각 도구에서 사용할 수 있는 기능이 제한되거나 입력검증이 구현되어 있는 경우"(입력 표준화), "도구 실행결과에 대한 검증 및 필터링이 구현되어 있는 경우"(출력 표준화)가 근거이나, MCP 프로토콜 자체의 메시지 스키마 규격 수준까지는 1순위 문헌이 다루지 않아 그 세부 형식까지는 확인 필요이다.

#### [3-2-다-2-02]: MCP Tool 호출 통제가 설계되었는가?
* **검토 내용**:
    * 사용자 권한 기반 Tool 호출 제한
    * 민감정보 포함 요청의 Tool 호출 차단
    * 외부 API 또는 외부 LLM 연계 Tool의 보안 검토 절차
* **출처 문헌**:
    * [AI위협매뉴얼] A01 평가기준[취약] — "사용자보다 더 높은 권한으로 도구를 실행하는 경우", "MCP 서버가 제한 없이 과도하게 넓은 권한을 가진 경우", "MCP 도구 호출에 대한 로깅이나 탐지 및 차단 프로세스가 구현되어 있지 않은 경우"
    * [AI보안가이드북] A-M04(화이트리스트 기반 도구 사용 — "AI가 사용할 수 있는 도구를 화이트리스트로 지정하여 관리하고, 타 도구 사용 시 차단"), A-M03(입・출력 필터링 — "AI가 프롬프트 인젝션 등 공격으로 인해 잘못된 도구를 호출하거나, 악성행위를 하지 못하도록 필터링을 수행")
    * [AI위협매뉴얼] 1.4 실행 권한 정보 분리 관리 — "MCP, 함수 등을 호출 시 API 키, 인증 토큰 등은 LLM이 직접 파라미터로 전달하지 않고, 별도의 방법을 통해 참조하도록 구현", "에이전트가 도구(또는 MCP) 호출을 시도할 때, 미들웨어 레이어가 개입하여 사용자 세션의 권한 정보를 참조한 뒤 호출 요청에 필요한 최소 권한만을 주입"
* **근거 및 상세내용**:
    * "사용자 권한 기반 Tool 호출 제한"은 A01 평가기준의 권한별 도구 제한 원칙과 1.4의 "사용자 세션의 권한정보를 참조한 뒤 최소권한만 주입"하는 미들웨어 구조가 직접 근거이다.
    * "민감정보 포함 요청의 Tool 호출 차단"은 A-M03(입・출력 필터링)이 직접 근거이며, 1.4의 "API키・인증토큰을 LLM컨텍스트와 분리 관리"가 민감정보(자격증명) 노출 차단의 기술적 근거이다.
    * "외부 API 또는 외부 LLM 연계 Tool의 보안 검토 절차"는 A-M04(화이트리스트 기반 도구사용)와 A01평가기준의 "MCP서버가 제한없이 과도하게 넓은 권한을 가진 경우"를 [취약]으로 규정한 것이 근거이며, [AI보안가이드북] 표9(A03 잘못된 도구사용 → A-M03・A-M04・A-M05 매핑)가 이를 뒷받침한다.

#### [3-2-다-2-03]: MCP 실행 로그 및 감사추적이 가능한가?
* **검토 내용**:
    * Tool 호출 이력, 파라미터, 응답값, 오류 로그 저장
    * Tool 호출 승인·차단·실패 이력 관리
    * 사고 발생 시 호출 경로 역추적 가능성
* **출처 문헌**:
    * [AI위협매뉴얼] A01 평가기준[양호]/[취약] — "MCP 도구 호출 이력이 기록되고 비정상적인 도구 호출이 탐지 및 차단되는 경우" / "MCP 도구 호출에 대한 로깅이나 탐지 및 차단 프로세스가 구현되어 있지 않은 경우"
    * [AI위협매뉴얼] 1.4 구현사례④ "도구 호출(Tool Invocation)" — "내부적으로는 도구 자체에서 권한 검증을 수행하거나, 외부 정책 엔진을 통해 검증이 이루어진다... 모든 호출 결과를 감사 로그에 기록하면 사용자의 권한, 요청 목적, 접근 리소스 간의 일관된 통제와 추적 가능성을 확보할 수 있다"
    * [AI보안가이드북] A-M05(에이전틱 AI 로깅・모니터링 — "AI가 호출하는 도구, 사용 자원량 등 전반적인 행위를 모니터링, 이상행위 발생여부를 탐지하여 대응"), A11(구성요소 취약점으로 인한 악성행위수행) 사례 "'Postmark-MCP' 이메일 유출 공격(´25.9.25)" — "MCP서버가 AI에이전트 및 공격자에게 수집한 이메일 동시전송" / 보안대책 "AI에이전트가 사용할 MCP서버, 외부도구 등에 대한 정기 취약점 점검을 실시하고, 보안업데이트 수행(A-M17)"
* **근거 및 상세내용**:
    * "Tool 호출 이력, 파라미터, 응답값, 오류로그 저장"은 A01평가기준이 "MCP 도구호출 이력이 기록"됨을 [양호]기준으로, 미기록을 [취약]기준으로 명시한 것이 직접 근거이다.
    * "Tool 호출 승인・차단・실패 이력관리"는 A-M05(로깅・모니터링)와 A01평가기준의 "비정상적인 도구호출이 탐지 및 차단되는 경우"가 근거이다.
    * "사고발생 시 호출경로 역추적 가능성"은 1.4구현사례④의 "감사로그... 사용자의 권한, 요청목적, 접근리소스 간의 일관된 통제와 추적가능성 확보"가 가장 직접적인 근거이며, 실제 발생한 'Postmark-MCP' 침해사례(MCP서버가 수집 이메일을 공격자에게도 동시전송)는 로그・추적체계 미비 시 실제로 발생하는 구체적 위험을 예시하여 본 항목의 필요성을 뒷받침한다.

## 3. A2A 연계 설계

#### [3-2-다-3-01]: Agent 간 통신 구조가 명확하게 설계되었는가?
* **검토 내용**:
    * Agent 간 역할, 호출 순서, 메시지 형식 정의
    * 요청 Agent, 수행 Agent, 검증 Agent 간 책임 경계
    * Agent 간 데이터 전달 범위 및 제한 기준
* **출처 문헌**:
    * [AI보안가이드북] "에이전트 통신" — "서로 다른 기능을 수행하는 에이전트 간에 계획, 상태정보, 메시지 등을 교환하며 협업하거나 조율", "구글의 A2A(Agent-to-Agent) 프로토콜 등 에이전트간 통신 프로토콜을 활용, 각 에이전트 간 통신을 수행"
    * [AI보안가이드북] A-M08(AI 에이전트 간 악성행위 전파 차단 — "AI 에이전트 간 통신 시 최소 권한만 부여하고, 엄격한 접근통제를 통해 유해・금지행위 전파를 차단")
    * [AI위협매뉴얼] 계층별 보안요구사항(에이전트 계층) — "다중 에이전트 환경에서는 각 에이전트의 역할과 권한을 최소화하여 불필요한 내부・외부 자원 접근을 차단해야 한다"
    * **(2026-08-13 추가조사・3순위 업계 사실상 표준)** Google 공식 A2A(Agent2Agent) 프로토콜 스펙(a2a-protocol.org, GitHub `a2aproject/A2A`) — 2025.4 Google이 공개(Apache-2.0)한 뒤 현재 Linux Foundation이 관리하는 개방형 에이전트 간 통신 표준으로, Agent Card(에이전트 능력을 기술하는 공개 JSON 메타데이터), Task(고유 ID와 상태 전이를 갖는 작업 단위), Message(role="user"/"agent"와 하나 이상의 Part로 구성되는 통신 턴)를 핵심 구성요소로 공식 정의한다. 이는 "Agent 간 역할・호출순서・메시지 형식 정의"라는 본 항목의 검토내용과 정확히 대응하는 국제 표준 프로토콜(현재 Linux Foundation 관리 하에 있어 특정 기업 종속성이 낮은 개방형 표준)이다.
* **근거 및 상세내용**:
    * "Agent간 역할, 호출순서, 메시지 형식 정의"는 A2A프로토콜 정의의 "계획, 상태정보, 메시지 등을 교환하며 협업・조율"이 직접 근거이다.
    * "요청Agent, 수행Agent, 검증Agent 간 책임경계"는 A-M08의 "에이전트간 통신시 최소권한만 부여, 엄격한 접근통제"라는 권한분리 원칙과 계층별요구사항의 "각 에이전트의 역할과 권한을 최소화"가 근거이다.
    * "Agent간 데이터전달 범위 및 제한기준"도 동일하게 A-M08 및 최소권한원칙이 근거이나, A2A 프로토콜 자체의 메시지 스키마(필드 구조) 수준의 세부 규격까지는 1순위 문헌에서 확인되지 않아 확인 필요이다.

#### [3-2-다-3-02]: A2A 호출 통제 및 충돌 방지 구조가 설계되었는가?
* **검토 내용**:
    * 중복 호출, 무한 루프, 반복 실행 방지 기준
    * Agent 간 상충 결과 발생 시 우선순위 기준
    * 호출 실패·지연·타임아웃 처리 기준
* **출처 문헌**:
    * [AI위협매뉴얼] A03(에이전트 DoS) 정의 — "에이전트 작업 시간, 반복 횟수, API 호출 빈도, 동시 실행 수에 대한 제한이 없거나 부적절한 경우 발생할 수 있다... 여러 에이전트가 서로에게 작업을 위임하는 순환 구조... 에서도 발생할 수 있다"
    * [AI위협매뉴얼] 진단방법 "(2) 멀티 에이전트 간 무한 위임 테스트" — "기획자 에이전트(A)와 실행 에이전트(B)가 있는 환경에서 '논리적으로 실행 불가능한 계획을 수립하고 실행하라'고 지시하여 A(수립)->B(실행불가, 반려)->A(재수립)->B(반려)...의 무한 루프 유도" / 대응방안 — "작업 시간 또는 반복 횟수 제한을 통한 무한 루프 방지(예시: LangChain 패키지에서 max_iterations 옵션을 사용하여 에이전트 최대 실행 횟수 제한), 사용자별・세션별 요청 횟수 제한, 반복 패턴과 실패 재시도를 탐지하여 자동 차단, API 호출 빈도와 타임아웃 관리로 외부 의존성 제어"
    * [AI보안가이드북] A10(AI 에이전트 간 통신 공격) — "잘못된 정보를 전달받은 AI 에이전트가 보안정책 우회 혹은 의도치 않은 명령을 수행하고, 잘못된 결과를 도출하여 의사 결정을 왜곡", 대책 A-M16(에이전틱 AI 통신구간 보호)
* **근거 및 상세내용**:
    * "중복호출, 무한루프, 반복실행 방지기준"은 A03정의의 "에이전트간 순환위임구조에서 DoS 발생"과 "멀티에이전트간 무한위임테스트" 시나리오(기획자-실행 에이전트 간 무한루프)가 검토내용과 사실상 동일한 상황을 다루는 가장 직접적인 근거이며, 대응방안의 "작업시간・반복횟수 제한(max_iterations)", "반복패턴 자동차단"이 구체적 통제기준을 제시한다.

    * [AI위협매뉴얼] 1.2 Human-in-the-Loop "가. 위험 기반 접근법" — "단순 정보 제공이나 일반적인 권고 사항은 자동으로 처리하되, 민감한 정보 접근이나 시스템 설정 변경과 같은 고위험 조치에 대해서만 인간 승인을 요구하는 방식"
    * [AI보안가이드북] A-M12(민감 명령 승인 절차 마련 — "도구 사용, 데이터 수정 등 과정에서 국가안보・사회안정에 영향을 미칠 수 있는 민감한 명령을 수행하기 전에 담당자 승인 절차를 마련")

* **근거 및 상세내용**:
    * "자동실행 가능업무와 승인필요업무 구분"은 HITL 위험기반접근법의 자동처리/승인요구 이분법이 정확히 대응하는 직접 근거이다.
    * "민원접수, 외부전송, 문서확정 등 사용자승인지점"은 1.3나의 "외부송금, 대량데이터전송과 같은 고위험행동... 승인절차(HITL)와 연계"가 직접 대응하는 근거이다(외부전송은 1.3나의 대량데이터전송 예시와 정확히 일치).
    * "고위험업무의 자동처리 제한기준"은 A-M12(민감명령 승인절차)가 직접 근거이다.

## 7. 다중 Agent 협업 설계

#### [3-2-다-7-01]: 다중 Agent 구성 및 역할 분담이 적정한가?

    * 검색 Agent, 응답 Agent, 문서생성 Agent, 검증 Agent 역할 구분

* **근거 및 상세내용**:

    * "Agent간 호출순서 및 데이터전달구조"는 A-M08(통신시 최소권한부여, 엄격한 접근통제)이 근거이다.
    * "Agent간 책임경계 및 예외처리기준"은 A-M06(미승인 에이전트로의 권한위임 차단)이 책임경계(권한위임 통제)의 직접 근거이다.

#### [3-2-다-7-02]: Agent 간 충돌 및 중복 실행 방지 구조가 설계되었는가?
* **검토 내용**:
    * 동일 요청에 대한 중복 Tool 호출 방지
    * 상충 결과 발생 시 우선순위 기준
    * 반복 실행, 무한 루프, 과도한 호출 방지
* **출처 문헌**:
    * [AI위협매뉴얼] A03(에이전트 DoS) 대응방안 — "작업 시간 또는 반복 횟수 제한을 통한 무한 루프 방지(예시: LangChain 패키지에서 max_iterations 옵션을 사용하여 에이전트 최대 실행 횟수 제한)", "사용자별, 세션별 요청 횟수 제한", "반복 패턴과 실패 재시도를 탐지하여 자동 차단", "API 호출 빈도와 타임아웃 관리로 외부 의존성 제어" / 사례 — "LLM 에이전트가 검색 도구를 1,000번 반복 호출하게 만들어 $1,000의 API 비용 발생"
* **근거 및 상세내용**:
    * "동일요청에 대한 중복Tool호출 방지"와 "반복실행, 무한루프, 과도한 호출 방지"는 A03대응방안의 max_iterations 예시코드 수준까지 구체화된 직접 근거이며, "$1,000 API비용 발생" 실제사례가 방지구조 미비 시의 실질적 위험을 뒷받침한다.
    * "상충결과 발생 시 우선순위기준"은 "멀티에이전트간 무한위임테스트" 시나리오(기획자에이전트A ↔ 실행에이전트B 간 상호반려로 인한 무한루프)가 상충상황의 전형적 사례를 제시하나, 상충 시 "우선순위"를 정하는 조정로직 자체는 1・2순위 문헌에서 확인되지 않아 확인 필요이다.

## 8. Agent 보안 및 권한 설계

#### [3-2-다-8-01]: Agent 실행 권한이 적정하게 설계되었는가?
* **검토 내용**:
    * 사용자·부서·직무별 Agent 사용 권한
    * Agent별 접근 가능한 데이터 및 Tool 범위
    * 관리자·운영자·일반사용자 권한 분리
* **출처 문헌**:
    * [AI위협매뉴얼] 1.1 최소 권한・역할 기반 접근 제어 — "AI 에이전트에게는 절대로 시스템 전체에 대한 포괄적인 권한을 부여해서는 안 되며, 요청자의 권한 수준과 동일하거나 그보다 제한된 범위 내에서만 자원에 접근하도록 해야 한다", "AI 에이전트의 권한은 역할별로 세분화하여 관리해야 하며, 불필요한 시스템 호출이나 외부 자원 접근은 기본적으로 차단해야 한다"
    * [AI보안가이드북] A-M11(과도한 권한부여 제한), A04(AI의 무단 권한 침해 — 위협 정의)
    * [감리점검해설서] SD11-2(시스템개발/분석/응용시스템) 검토항목 "05. 사용자 접근/통제 및 보안에 대한 설계가 수행되었는가? — 사용자별/그룹별/업무별 접근권한, 감사기능"
    * **(2026-08-13 추가조사・업계 사실상 표준을 넘어선 국가공인표준)** ANSI/INCITS 359(RBAC) — NIST 제안, ANSI 국가표준으로 채택된 RBAC 참조모델. 사용자・역할・권한・오퍼레이션・객체를 기본요소로 하는 Core/Hierarchical/Constraint RBAC 모델을 공식 규정하며, "관리자・운영자・일반사용자 권한 분리"는 이 표준의 역할 계층(Hierarchical RBAC)을 실무 적용한 사례에 해당한다.
* **근거 및 상세내용**:
    * "사용자・부서・직무별 Agent사용권한"과 "Agent별 접근가능한 데이터 및 Tool범위"는 1.1의 "요청자의 권한수준과 동일하거나 그보다 제한된 범위내에서만 자원접근", "역할별 세분화 관리"가 직접 근거이며, A-M11이 이를 보강한다.
    * "관리자・운영자・일반사용자 권한분리"는 [감리점검해설서] SD11-2의 "사용자별/그룹별/업무별 접근권한" 검토기준이 일반 감리방법론상 근거이나, "관리자/운영자/일반사용자"라는 3단계 구분을 Agent 맥락에서 명시한 조항은 1순위 AI특화문헌에서 확인되지 않아 확인 필요이다.

#### [3-2-다-8-02]: Agent 오남용 방지 구조가 설계되었는가?
* **검토 내용**:

* **출처 문헌**:
    * [AI보안가이드북] A-M03(입・출력 필터링 — "AI가 프롬프트 인젝션 등 공격으로 인해 잘못된 도구를 호출하거나, 악성행위를 하지 못하도록 필터링을 수행"), A-M04(화이트리스트 기반 도구사용), A-M11(과도한 권한부여 제한)
    * [AI위협매뉴얼] A02(에이전트 하이재킹) 정의 — "외부데이터(웹페이지, 문서 등)에 숨겨진 악성 프롬프트를 에이전트가 정상지시로 착각해 의도치않은 작업을 수행하는 위협"
    * [AI위협매뉴얼] 3.6 요청 트래픽 제어 설정 표 — "사용자・세션 제한", "동시 추론 제한", "작업 시간・반복 횟수 제한"
* **근거 및 상세내용**:

    * "Agent 실행횟수, 호출빈도, 자원사용 제한"은 3.6의 트래픽제어 표(사용자・세션제한, 동시추론제한, 작업시간・반복횟수제한)가 직접 근거이다.

## 9. Human-in-the-Loop 설계

#### [3-2-다-9-01]: 사람 검토 및 승인 지점이 명확히 설계되었는가?
* **검토 내용**:

* **출처 문헌**:

* **근거 및 상세내용**:

    * "Agent결과의 담당자 검토・수정・확정절차"는 1.2나의 "사용자가 AI의 제안내용을 명확히 이해할 수 있도록 충분한 맥락정보를 제공"하는 UI설계 원칙이 검토・수정을 위한 정보제공 요건의 근거이다.

#### [3-2-다-9-02]: Agent 실패 시 인간 개입 절차가 설계되었는가?
* **검토 내용**:
    * 정보 부족, 권한 부족, 오류 발생 시 담당자 연결
    * 반복 실패 또는 민감 민원 발생 시 escalation 기준
    * 사용자 불만 및 오답 신고 처리 절차
* **출처 문헌**:
    * [AI보안가이드북] A09(과도한 인간 개입 유발로 과부하 발생 — "AI 에이전트의 의사 결정, 실행 결과물 등에 대한 과도한 담당자 개입 요청을 발생... 빈번한 개입 요청으로 담당자의 업무수행을 방해하고, 승인 피로 누적으로... 잘못된 의사결정 유발"), 대책 A-M13(민감 명령 승인 요청 임계값 설정)
    * [AI위협매뉴얼] 1.5 실시간 모니터링 "나. 주요 고려 사항 — 탐지된 이상 행동에 대해서는 작업 중단, 권한 회수, 관리자 알림 등 즉각적인 대응이 이루어지도록 운영 프로세스를 마련"
    * [이용자보호가이드라인] Ⅴ.1 이용자 인격권 보호 — "내부 모니터링 체계나 이용자 신고 프로세스 등 관련 방안을 마련하도록 노력한다"; 부록 실행사례 — "이용자가 신고한 경우 해당 콘텐츠에 대한 검증 및 조치를 위한 절차를 마련하고 적절한 조치를"
* **근거 및 상세내용**:
    * "정보부족, 권한부족, 오류발생 시 담당자연결"은 1.5나의 "이상행동에 대해 작업중단, 권한회수, 관리자알림 등 즉각대응 운영프로세스"가 직접 근거이다.
    * "반복실패 또는 민감민원 발생시 escalation기준"은 A09(과도한 인간개입 유발) 위협정의가 escalation 설계 시 유의해야 할 반면교사적 근거(과도한 승인요청으로 인한 승인피로 위험)를 제공하고, A-M13(임계값설정)이 이를 방지하면서도 escalation을 유지하는 균형점의 근거이다.
    * "사용자불만 및 오답신고 처리절차"는 [이용자보호가이드라인] Ⅴ.1의 "이용자 신고프로세스" 및 부록 실행사례의 "신고된 콘텐츠에 대한 검증 및 조치 절차"가 직접 근거이다(본 조사에서 원문을 재확인함).

## 10. Agent 품질 및 성능평가 설계

#### [3-2-다-10-01]: Agent 품질평가 기준이 설계되었는가?
