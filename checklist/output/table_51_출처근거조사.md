## 1. Agentic AI 구현 완료 및 과업이행 점검

#### [3-3-다-1-01]: Agentic AI 기능이 요구사항대로 구현되었는가?
* **검토 내용**:
    * 업무별, 영역별 Agent 구현 여부
    * 단일 Agent 및 다중 Agent 적용 범위 구현 여부
    * Agent별 역할, 책임, 처리 범위의 최종 반영 여부
* **출처 문헌**:
    * [수행가이드] 요구정의단계 감리, 소프트웨어 요구사항 품질 매트릭 — "* 출처: TTAK.KO-11.0103 소프트웨어 요구사항품질 평가 항목(2010.12.23.)" — 품질특성 "완전성(Completeness)", "정확성(Correctness)", "추적성(Traceability)"; 설계단계 감리 "대비표는 과업대비표와 요구사항추적표를 통칭... 모든 요구사항이 산출물에 반영되었는지는 요구사항추적표로 관리되고 추적되어야 한다"
    * [AI보안가이드북] 제3장 제1절 가.개념도, 에이전틱 AI(Agentic AI) 정의 — "특정 목표를 해결하기 위해 다수 AI 에이전트가 상호 작용하며 계획수립, 외부 정보 기억, 도구 호출 등을 사용자의 개입없이 자율성을 가지고 수행"; "(요청)사용자가 에이전틱AI에 임무요청 → (계획)에이전트별 목표달성을 위한 행동방침수립 → (행동)외부도구 등을 활용, 작업수행"
    * [AI위협매뉴얼] 제1장 개요 — "에이전트는 LLM이 목표 달성을 위해 자율적으로 도구를 호출하며 단계별 작업을 수행하는 실행 단위이다. 다중 에이전트(Multi-Agent) 시스템은 복수 에이전트가 협력·상호 작용하여 복잡한 작업을 처리한다."
* **근거 및 상세내용**:
    * TTAK.KO-11.0103 기반의 요구사항추적표·대비표 방법론은 "구현이 요구사항대로 되었는지"를 판정하는 감리의 표준 절차(요구사항 → 세부 검사항목 → 검사기준의 추적)를 제공하며, 이는 본 항목이 종료단계에서 점검해야 할 절차적 근거를 직접 이룬다.
    * "업무별, 영역별 Agent 구현 여부"와 "단일 Agent 및 다중 Agent 적용 범위"는 [AI위협매뉴얼]의 다중 에이전트(Multi-Agent) 정의("복수 에이전트가 협력·상호작용")에서 직접적 개념 근거를 찾을 수 있다.
    * "Agent별 역할, 책임, 처리 범위의 최종 반영"은 [AI보안가이드북]의 "계획"요소(질의 분해 → 단계적 행동지침 수립) 및 에이전틱 AI 정의(다수 에이전트의 상호작용)에서 부분적 근거를 찾을 수 있으나, Agent별 역할·책임을 정의하는 공식 산출물 양식이나 판정기준을 규정한 조문은 확인되지 않았다 — 확인 필요.

* **검토 내용**:

    * Agent 실행 중단, 재시도, 예외처리 동작 여부
    * Agent 실패 시 담당자 전환 또는 대체 처리 동작 여부
* **출처 문헌**:
    * [AI보안가이드북] 그림32 개념도 및 요소별 설명 — 계획/메모리(단기·장기)/도구호출/에이전트통신 4대 구성요소; MCP 정의 "(요청)AI 에이전트가 요청 해석, 계획을 수립하여 MCP 서버 전달 → (작업)MCP 서버는 외부 시스템과 상호작용, 실제 작업 수행"; A-M07(AI 에이전트 자동 중단) "미리 설정한 유해·금지행위를 AI 에이전트가 수행하려고 하거나, 잘못된 목표가 설정되었거나, 자원 소비 임계값을 초과할 경우 자동으로 중단되도록 구성"
    * [AI위협매뉴얼] H02(자율성으로 인한 통제상실 위협) — "에이전트 폭주 등 자원 과도 소모 시 즉각적으로 권한과 세션을 강제 종료하는 비상 정지(Kill-Switch) 절차가 있는가", "파일·설정 변경, API 호출 등 에이전트의 실행 결과를 이전 상태로 되돌릴 수 있는 롤백 기능이 마련되어 있는가"
* **근거 및 상세내용**:
    * [AI보안가이드북]의 "(요청)→(계획)→(행동)" 흐름과 계획/도구호출 요소 설명은 "사용자요청 → 계획수립 → Tool호출 → 응답"이라는 검토내용의 상위 개념적 골격을 직접 뒷받침한다. 다만 "의도분석"과 "결과검증"을 개념도가 별도의 독립 단계로 명시하지는 않아, 검토항목이 요구하는 5단계 흐름 중 이 두 단계는 세부적으로 확인되지 않았다 — 확인 필요.
    * "Agent 실행 중단, 재시도, 예외처리"는 [AI보안가이드북] A-M07(자동중단)과 [AI위협매뉴얼] H02의 Kill-Switch·롤백 기능에서 직접적이고 구체적인 근거를 확보하였다.
    * "Agent 실패 시 담당자 전환 또는 대체 처리"는 H02의 관리자 승인(HITL) 강제 원칙과 연결되는 담당자 개입 개념에서 근거를 찾을 수 있으나, "대체 Agent로의 자동 전환(failover)" 메커니즘 자체를 규정한 조문은 확인되지 않았다 — 확인 필요.

## 3. A2A 연계 및 Agent 간 협업 검증

#### [3-3-다-3-01]: Agent 간 통신 구조가 정상 동작하는가?
* **검토 내용**:
    * Agent 간 역할, 호출 순서, 메시지 형식 적용 여부
    * 요청 Agent, 수행 Agent, 검증 Agent 간 데이터 전달 정상 여부
    * Agent 간 책임 경계 및 처리 결과 구분 여부
* **출처 문헌**:
    * [AI보안가이드북] 요소별 설명 "에이전트 통신: 서로 다른 기능을 수행하는 에이전트 간에 계획, 상태 정보, 메시지 등을 교환하며 협업하거나 조율", "구글의 A2A(Agent-to-Agent) 프로토콜 등 에이전트간 통신 프로토콜을 활용, 각 에이전트 간 통신을 수행"; A-M15(AI 에이전트 신원 확인) "협업할 AI 에이전트가 적합한 인증 혹은 신원을 보유하고 있는지 상호 검증"
    * **(2026-08-13 추가조사・3순위 업계 사실상 표준)** Google 공식 A2A(Agent2Agent) 프로토콜 스펙(a2a-protocol.org, 현재 Linux Foundation 관리, Apache-2.0) — AgentCard(에이전트 능력 공시), Task 상태 전이(submitted→working→completed/failed), 메시지·아티팩트 교환 스키마를 JSON-RPC 기반으로 공식 규정한다. "Agent 간 역할, 호출 순서, 메시지 형식 적용 여부"의 "정상 동작"을 판정하려면 이 공식 스펙의 메시지·상태 스키마 준수 여부를 실제 검증 기준으로 삼는 것이 업계 표준 방법이다.
* **근거 및 상세내용**:
    * A2A 정의("계획, 상태 정보, 메시지 등을 교환하며 협업·조율")는 "Agent 간 역할, 호출 순서, 메시지 형식 적용 여부"라는 검토내용에 대한 직접적 정의적 근거를 제공한다.
    * "요청 Agent, 수행 Agent, 검증 Agent 간 데이터 전달"은 다중 에이전트 협업 개념의 구체화이며, A-M15(신원 확인)가 통신 상대 Agent의 정당성을 사전에 검증하는 절차적 근거를 보강한다.
    * "Agent 간 책임 경계 및 처리 결과 구분"은 "서로 다른 기능을 수행하는 에이전트"라는 전제에서 기능·책임 분리가 개념적으로 내포되어 있으나, 이를 판정하는 세부 기준을 직접 규정한 조문은 확인되지 않았다 — 확인 필요.

#### [3-3-다-3-02]: A2A 호출 통제 및 충돌 방지가 적용되었는가?
* **검토 내용**:
    * 중복 호출, 무한 루프, 반복 실행 방지 기능 동작 여부
    * Agent 간 상충 결과 발생 시 우선순위 적용 여부
    * 호출 실패·지연·타임아웃 처리 결과 확인
* **출처 문헌**:
    * [AI위협매뉴얼] A03(에이전트 DoS) — "에이전트가 무한 루프나 과도한 API 호출을 발생시켜 시스템 자원과..."(서비스 가용성 위협); 체크리스트 "에이전트 작업 실행 시간에 대한 적절한 제한을 설정하는가", "비정상적인 작업 패턴 탐지 및 자동 중단 기능이 있는가", "동시 실행 가능한 작업 수에 대한 제한이 있는가"
    * [AI보안가이드북] A-M08(AI 에이전트 간 악성행위 전파 차단) — "AI 에이전트 간 통신 시 최소 권한만 부여하고, 엄격한 접근통제를 통해 유해·금지행위 전파를 차단"; A-M07(AI 에이전트 자동 중단)
* **근거 및 상세내용**:
    * "중복 호출, 무한 루프, 반복 실행 방지"는 [AI위협매뉴얼] A03(에이전트 DoS)의 정의("무한 루프나 과도한 API 호출") 및 체크리스트("동시 실행 작업 수 제한", "비정상 패턴 자동 중단")와 문언 수준으로 정확히 대응하는 가장 직접적인 근거이다.
    * "호출 실패·지연·타임아웃 처리 결과"는 A03의 "작업 실행 시간에 대한 적절한 제한"에서 근거를 확보하였다.
    * "Agent 간 상충 결과 발생 시 우선순위 적용 여부"는 A-M08(전파 차단·접근통제)의 원칙과 간접적으로 연결되나, 서로 다른 Agent의 결과가 상충할 때 이를 해소하는 우선순위 규칙을 직접 규정한 조문은 1순위 문헌에서 확인되지 않았다 — 확인 필요.

#### [3-3-다-3-03]: A2A 결과 검증 및 책임추적이 가능한가?
* **검토 내용**:
    * Agent별 처리 결과와 최종 응답 간 정합성 확인
    * Agent 간 호출 이력 및 의사결정 경로 기록 여부
    * 최종 응답 생성 책임 Agent 식별 가능 여부
* **출처 문헌**:
    * [AI보안가이드북] A08(위협: AI로 인한 사고·이상행위 탐지 불가) — "AI의 추론·판단·행위 과정에 대한 로그·모니터링 부족으로 사고 발생 시 동작과정 추적 및 **책임소재 규명** 한계"; A-M05(로깅·모니터링); A-M14(설명 가능한 AI 구성) "AI의 추론·결정 과정 등을 담당자가 인지 가능한 형태로 필요한 정보를 제공할 수 있는 체계 마련"
    * [AI위협매뉴얼] H02 — "에이전트의 도구 선택 사유와 다단계 추론 과정을 투명하게 기록하여 사후 감사가 가능하도록 관리하는가"
* **근거 및 상세내용**:
    * A08의 위협정의에 등장하는 "책임소재 규명"이라는 표현은 본 항목의 "최종 응답 생성 책임 Agent 식별 가능 여부"와 문언적으로 정확히 대응한다. A-M14(설명 가능한 AI)와 [AI위협매뉴얼] H02(사후 감사 가능한 투명한 기록)는 "Agent별 처리 결과와 최종 응답 간 정합성 확인", "Agent 간 호출 이력 및 의사결정 경로 기록"의 직접 근거이다.
    * 다만 다수 Agent 중 최종 책임 Agent를 지정·식별하는 구체적 절차나 판정기준을 규정한 조문은 확인되지 않았다 — 원칙(A08의 책임소재 규명 필요성, A-M14의 설명가능성 체계)은 확립되어 있으나 실행기준은 사업별 수립이 필요하다 — 확인 필요.

## 4. Agent–RAG 연계 검증

#### [3-3-다-4-01]: Agent와 RAG 검색 연계가 정상 동작하는가?
* **검토 내용**:
    * Agent의 RAG 대상 데이터 및 검색 범위 호출 정상 여부
    * 기록물관리, 민원통합, 사규, FAQ별 검색 호출 결과 확인
    * 검색 결과가 Agent 응답에 정상 반영되는지 확인
* **출처 문헌**:
    * [AI보안가이드북] 요소별 설명 "메모리 — 장기 메모리: 외부 지식, 과거 사용자 상호작용 등 개인화 정보를 축적하고 있는 **RAG 벡터DB 등 저장소**"
    * [AI위협매뉴얼] M02(벡터DB·임베딩 유출) — "벡터 DB 및 임베딩 저장소에 대한 접근 권한을 통제하는가", "벡터 DB 또는 RAG 검색 결과에 포함된 민감정보가 모델 출력에 노출되지 않도록 관리하는가"; A04(에이전트 메모리 오염) "에이전트 장기 메모리(RAG DB, 파일 등)에 인증 및 권한 제어를 적용하는가"
* **근거 및 상세내용**:
    * [AI보안가이드북]이 RAG 벡터DB를 에이전트의 "장기 메모리" 구성요소로 명시적으로 정의하는 것은 "Agent의 RAG 대상 데이터 및 검색 범위 호출"이라는 검토내용의 구조적 근거이다.
    * M02·A04의 "벡터DB/RAG DB 접근 권한 통제, 인증·권한 제어"는 "검색 결과가 Agent 응답에 정상 반영되는지"를 확인하기 이전에 전제되어야 할 접근통제 요건으로서 근거를 이룬다.
    * "기록물관리, 민원통합, 사규, FAQ별 검색 호출 결과 확인"이라는 업무영역별 RAG 소스 구분은 1순위 문헌이 다루는 일반적 AI시스템 위협·대책 범위를 벗어나는 기관별 업무 특수사항으로, 해당 세부 기준은 확인 필요.

#### [3-3-다-4-02]: 검색 결과 검증 및 근거 활용이 적정한가?
* **검토 내용**:
    * Agent가 활용한 근거 문서의 출처 표시 여부
    * 관련도 낮은 검색 결과 제외 여부
    * 근거 부족 시 추가질의 또는 답변 제한 동작 여부
* **출처 문헌**:
    * [AI위협매뉴얼] M05(환각) — "모델이 거짓 정보(환각)나 허위 근거를 생성할 가능성을 정기적으로 평가하는가", "**중요한 답변에 대해 출처 확인 및 근거를 제시하도록 검증 절차를 수행하는가**", "사용자에게 AI의 답변에 오류나 환각이 포함될 수 있음을 명확히 고지하는가"
    * [AI위협매뉴얼] A04(에이전트 메모리 오염) — "장기 메모리에 저장되는 항목에 대해서 금칙어 필터링, 명령 패턴 차단, 정책 기반 검증 절차가 있는가", "장기 메모리 데이터에 대해 주기적으로 무결성을 검토하고 이상 징후를 탐지하는가"
* **근거 및 상세내용**:
    * M05의 "중요한 답변에 대해 출처 확인 및 근거를 제시하도록 검증 절차를 수행하는가"는 "Agent가 활용한 근거 문서의 출처 표시 여부"라는 검토내용과 문언 수준으로 정확히 대응하는 가장 직접적인 근거이다.
    * "근거 부족 시 추가질의 또는 답변 제한 동작 여부"는 M05의 "환각 생성 가능성 정기 평가" 및 "오류·환각 포함 가능성 고지" 원칙에서 도출되는 대응조치로서 근거를 확보하였다.
    * "관련도 낮은 검색 결과 제외 여부"는 A04의 "정책 기반 검증 절차"에서 개념적으로 유추되나, RAG 검색 결과의 관련도(relevance) 재순위화·필터링 기준을 직접 규정한 조문은 확인되지 않았다 — 확인 필요.

    * "Tool 결과와 Agent 응답 간 정합성 확인"은 [AI보안가이드북] A-M10(입·출력 결과 검증)에서 직접 근거를 찾을 수 있다(다만 A-M10의 원 정의는 "사용자 입력–AI 출력" 일치 검증이며, 이를 "Tool 결과–Agent 응답" 정합성 확인으로 유추 확장 적용한 것임을 밝혀둔다).

## 6. 계획 수립 및 실행 통제 검증

#### [3-3-다-6-02]: Agent의 자율 실행 범위가 통제되는가?
* **검토 내용**:
    * 자동 실행 가능 업무와 승인 필요 업무 구분 적용 여부
    * 민원 접수, 외부 전송, 문서 확정 등 사용자 승인 지점 동작 여부
    * 고위험 업무의 자동처리 제한 적용 여부
* **출처 문헌**:

    * [AI보안가이드북] A-M12(민감 명령 승인 절차 마련) — "도구 사용, 데이터 수정 등 과정에서 국가안보·사회안정에 영향을 미칠 수 있는 민감한 명령을 수행하기 전에 담당자 승인 절차를 마련"; A-M11(과도한 권한 부여 제한)
* **근거 및 상세내용**:
    * H02의 "파급력이 큰 작업 수행 전 관리자 명시적 승인(HITL)"과 [AI보안가이드북] A-M12의 "민감 명령 승인 절차"는 "자동 실행 가능 업무와 승인 필요 업무 구분 적용 여부"의 가장 직접적인 근거이며, "민원 접수, 외부 전송, 문서 확정 등 사용자 승인 지점"은 이 HITL 강제 지점의 업무적 구체화에 해당한다.
    * "고위험 업무의 자동처리 제한"은 A-M11(과도한 권한 부여 제한) 및 H02의 승인 강제 원칙에서 직접 근거를 확보하였다.

#### [3-3-다-7-02]: Agent 오남용 방지 기능이 동작하는가?

## 8. Human-in-the-Loop 검증

#### [3-3-다-8-01]: 사람 검토 및 승인 절차가 정상 동작하는가?
* **검토 내용**:
    * 민원 답변, 문서생성, 외부 전송 등 승인 필요 업무 처리 여부
    * Agent 결과의 담당자 검토·수정·확정 절차 적용 여부
    * 자동처리와 수동처리 전환 기준 동작 여부
* **출처 문헌**:
    * [AI위협매뉴얼] H02 — "파급력이 큰 작업(데이터 삭제, 외부 송금 등) 수행 전, 반드시 관리자의 명시적 승인(**Human-in-the-Loop**)을 거치도록 강제하는가"
    * [AI보안가이드북] A-M12(민감 명령 승인 절차 마련), A-M13(민감 명령 승인 요청 임계값 설정)
* **근거 및 상세내용**:
    * H02는 "Human-in-the-Loop"라는 용어 자체를 원문 그대로 명시하는 1순위 문헌으로서, 항목 8-01 전체("민원답변, 문서생성, 외부전송 등 승인필요업무", "담당자 검토·수정·확정 절차")의 직접적·원칙적 근거이다.
    * "자동처리와 수동처리 전환 기준"은 A-M12(민감 명령 승인 절차)와 A-M13(승인 요청 임계값 설정 — 민감 명령 우선순위에 따라 임계값을 설정)에서 근거를 확보하였다. A-M13의 "임계값"이 자동/수동 전환의 정량적 기준을 설정하는 방식의 근거가 된다.

#### [3-3-다-8-02]: Agent 실패 시 인간 개입 절차가 작동하는가?
* **검토 내용**:
    * 정보 부족, 권한 부족, 오류 발생 시 담당자 연결 여부
    * 반복 실패 또는 민감 민원 발생 시 escalation 처리 여부
    * 사용자 불만 및 오답 신고 처리 절차 동작 여부
* **출처 문헌**:
    * [AI위협매뉴얼] H02 — "에이전트 폭주 등 자원 과도 소모 시 즉각적으로 권한과 세션을 강제 종료하는 비상 정지(**Kill-Switch**) 절차가 있는가"
    * [AI보안가이드북] A09(위협: 과도한 인간 개입 유발로 과부하 발생) "AI 에이전트의 의사 결정, 실행 결과물 등에 대한 과도한 담당자 개입 요청을 발생"; A-M13(민감 명령 승인 요청 임계값 설정)
    * [이용자보호가이드라인] "서비스 제공자는... 이용자가 산출물이 편향적이라고 판단하였을 때 바로 **신고할 수 있는 직관적인 방법을 제공하고 신고 내용을 처리하는 절차를 마련**한다"; "내부 모니터링 체계나 **이용자 신고 프로세스** 등 관련 방안을 마련하도록 노력한다"
* **근거 및 상세내용**:
    * "정보 부족, 권한 부족, 오류 발생 시 담당자 연결"은 H02의 Kill-Switch 절차 및 A-M12(승인 절차) 원칙의 연장선에서 근거를 확보하였다.
    * "반복 실패 또는 민감 민원 발생 시 escalation 처리"는 A09 위협("과도한 인간 개입 유발로 과부하 발생")의 대책인 A-M13(임계값 설정을 통한 승인 요청 조절)에서 근거를 이룬다.
    * "사용자 불만 및 오답 신고 처리 절차"는 [이용자보호가이드라인]의 "이용자 신고 프로세스", "신고할 수 있는 직관적인 방법 제공 및 신고 내용 처리 절차"에 문언 수준으로 정확히 대응하는 가장 직접적인 근거이다.

## 9. Agent 품질 및 성능평가 검증

    * "업무처리 결과와 근거 문서 간 정합성 검증"은 M05의 "출처확인 및 근거제시 검증절차"에서 근거를 확보하였다. "대민서비스와 내부업무 Agent 품질기준 충족여부"처럼 서비스 유형별로 차등화된 품질기준을 규정한 조문은 확인되지 않았다 — 확인 필요.

    * [AI보안가이드북] A-M05(에이전틱 AI 로깅·모니터링); A-M17(에이전틱 AI 구성요소 취약점 점검) "MCP 서버 등 구성요소에 대해 정기적으로 취약점을 확인하고 보안업데이트 등 실시"
    * [AI위협매뉴얼] S04(취약한 버전의 에이전트 확장요소 사용) "사용 중인 에이전트 확장요소에 알려진 보안 취약점이 존재하는지 정기적으로 점검하는가"; A03(에이전트 DoS) "비정상적인 작업 패턴 탐지"
* **근거 및 상세내용**:
    * MA-DS-01은 "모니터링 대상/관리항목 선정 → 절차수립 → 결과기록"이라는 감리절차 표준을 제공하는 포괄적 근거이며, A-M05가 이를 "AI가 호출하는 도구, 사용 자원량 등"이라는 Agent·MCP 특유 대상으로 구체화한다.
    * "MCP Tool 호출 성공률, 지연시간, 장애율 모니터링"은 MA-DS-01·MA-DS-04(성능관리)의 결합에서, "A2A 호출 흐름, 반복 호출, 비정상 실행 탐지"는 [AI위협매뉴얼] A03(에이전트 DoS)의 "비정상적인 작업 패턴 탐지"에서 근거를 확보하였다.
    * A-M17·S04는 "MCP 서버 등 구성요소"의 정기적 취약점 점검을 명시하여 Agent/MCP 모니터링의 보안 측면을 뒷받침한다.

#### [3-3-다-10-03](B): Agent 개선 및 재평가 체계가 마련되었는가?

## 11. Agent 산출물 및 증적관리 점검

#### [3-3-다-11-01]: Agent 관련 최종 산출물이 완비되었는가?
* **검토 내용**:
    * Agent 아키텍처 설계서, Agent 목록, 업무 시나리오 정의서 제출 여부
    * MCP Tool/API 목록, 호출조건, 권한 매트릭스 제출 여부
    * A2A 메시지 정의서, Agent 간 호출흐름도, 오류처리 기준 제출 여부
* **출처 문헌**:
    * [구축운영지침] 제44조(표준산출물) ① — "행정기관등의 장은 운영, 유지관리 등에 필요한 표준산출물을 지정하여 사업자에게 제출을 요구할 수 있다"
    * [수행가이드] 설계단계 감리 — 대비표(과업대비표, 요구사항추적표), 검사기준서 개념(요구사항 → 검사항목 → 검사기준의 추적 관리)
* **근거 및 상세내용**:
    * 제44조①은 발주기관이 사업자에게 운영·유지관리에 필요한 산출물 제출을 요구할 수 있는 법적 근거를 제공하며, 이는 "Agent 아키텍처 설계서, Agent 목록, 업무 시나리오 정의서" 등 종료단계 표준산출물 제출 요구의 상위 법적 근거를 이룬다.
    * "MCP Tool/API 목록, 호출조건, 권한 매트릭스"와 "A2A 메시지 정의서, Agent 간 호출흐름도, 오류처리 기준"이라는 개별 산출물 명칭 자체를 규정한 조문은 확인되지 않았으나, [수행가이드]의 대비표·검사기준서 방법론(요구사항 → 세부검사항목 → 검사기준의 추적)을 MCP/A2A 영역에 적용한 것으로 볼 수 있다 — 개별 산출물의 표준 양식·필수기재사항은 확인 필요.

#### [3-3-다-11-02]: Agent 검증 증적이 확보되었는가?
* **검토 내용**:
    * Agent 실행 로그, MCP Tool 호출 로그, A2A 호출 로그 확보 여부
    * 테스트 시나리오 및 수행결과 증적 확보 여부
    * Agent 보안통제 및 권한검증 증적 확보 여부
* **출처 문헌**:
    * [지능정보기술가이드] MA-DS-13[릴리즈 및 배포관리(운영이관)] 01 — "변경요청 결과를 확인하기 위한 시험계획을 수립하고, 시나리오 및 데이터에 의한 검증을 실시하는가"
    * [AI위협매뉴얼] H02 — "에이전트의 도구 선택 사유와 다단계 추론 과정을 투명하게 기록하여 사후 감사가 가능하도록 관리하는가"
    * [AI보안가이드북] A-M05(로깅·모니터링)
* **근거 및 상세내용**:
    * MA-DS-13의 "시험계획·시나리오·데이터에 의한 검증"은 "테스트 시나리오 및 수행결과 증적 확보 여부"의 직접 근거이며, H02의 "사후 감사 가능한 기록관리"는 "Agent 실행 로그, MCP Tool 호출 로그, A2A 호출 로그 확보"의 직접 근거이다.
    * "Agent 보안통제 및 권한검증 증적"은 A-M05(로깅·모니터링) 및 카테고리 7(Agent 보안 및 권한 검증)의 각 대책이 산출하는 로그·기록물이 증적으로 활용됨을 근거로 한다.

## 12. 운영전환 및 잔여위험 관리

#### [3-3-다-12-01]: Agentic AI 운영전환 준비가 완료되었는가?
* **검토 내용**:
    * Agent 운영절차 및 장애 대응절차 인계 여부
    * Agent별 운영 담당자 교육 및 권한 인계 여부
    * Agent/MCP/A2A 운영 모니터링 기준선 확정 여부
* **출처 문헌**:
    * [지능정보기술가이드] MA-DS-13[릴리즈 및 배포관리(운영이관)] 04 — "반영 시 오류를 최소화하기 위해 이관 작업 주체인 운영 조직과 협업 절차에 따라 특이사항 공유 및 회의 등 협업을 이행하고 있는가"
    * [구축운영지침] 제59조(운영 및 유지관리) ①③, 제59조의2(정보시스템 장애 대응체계 관리) ①
* **근거 및 상세내용**:
    * MA-DS-13의 "이관 작업 주체인 운영 조직과의 협업 절차"는 "Agent 운영절차 및 장애 대응절차 인계 여부"의 직접 근거이며, [구축운영지침] 제59조③의 "사업자는... 반복적으로 수행하는 사항을 매뉴얼로 작성·관리하고, 행정기관등의 장이 요구하는 경우 제공"이 운영절차 인계의 법적 근거를 보강한다. 제59조의2①의 장애대응체계(외부전문가 활용체계 구성) 요구가 장애대응절차 인계의 근거를 이룬다.
    * "Agent별 운영 담당자 교육 및 권한 인계 여부"는 MA-DS-13의 운영조직 협업절차 개념에서 유추되나, "교육"을 명시적으로 요구하는 조문은 이 항목에서 명확히 확인되지 않았다 — 확인 필요.
    * "Agent/MCP/A2A 운영 모니터링 기준선 확정 여부"는 카테고리 10에서 확보한 MA-DS-01(모니터링)·A-M05 체계가 운영전환 시점에 공식화되는 것으로 유추할 수 있으나, "기준선(baseline)" 개념 자체를 명시한 조문은 확인되지 않았다 — 확인 필요.

#### [3-3-다-12-02]: 잔여위험 및 후속 개선과제가 정리되었는가?
* **검토 내용**:
    * Agent 오답, Tool 오류, A2A 충돌 등 잔여위험 식별 여부
    * 운영 중 보완 필요사항 및 후속 개선과제 정리 여부
    * 2·3차 확산을 위한 Agent 적용 기준 및 개선사항 정리 여부
* **출처 문헌**:
    * [구축운영지침] 제49조(감리시행) ① — "행정기관등의 장과 사업자는 단계별 감리수행결과보고서에 따라 시정조치를 수행하여야 한다"
    * [지능정보기술가이드] MA-DS-07[장애관리] — "재발 방지를 위한 계획 수립, 수행 및 관련 팀과 공유"
* **근거 및 상세내용**:
    * 제49조①의 "감리수행결과보고서에 따른 시정조치"는 감리에서 식별된 미비사항에 대한 후속조치를 법적으로 강제하는 조항으로서, "운영 중 보완 필요사항 및 후속 개선과제 정리 여부"의 상위 법적 근거이다. MA-DS-07의 "재발 방지를 위한 계획 수립"은 "Agent 오답, Tool 오류, A2A 충돌 등"에 대한 지속적 개선과제 관리의 실무적 근거를 보강한다.
    * "잔여위험(residual risk)"이라는 용어 자체를 정의하거나 그 식별·관리 절차를 규정한 조문은 1순위 문헌 11종 어디에서도 확인되지 않았다. 2순위로 국가법령정보센터(law.go.kr)에서 「정보시스템 감리기준」(행정안전부고시 제2024-53호) 원문 확인을 시도하였으나, 해당 페이지가 스크립트 기반 동적로딩 구조여서 WebFetch로 조문 본문을 확보하지 못하였다(위 "조사에 사용한 출처문헌 > 2순위" 참조) — "잔여위험" 용어의 공식 정의 및 "2·3차 확산을 위한 Agent 적용 기준"은 확인 필요로 명시한다.
